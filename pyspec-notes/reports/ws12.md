### Rules and concepts added
1. **`slotdefs[]` is the source of truth for dunder ↔ slot.**
   - The new `Tools/clinic/libclinic/pyspec/slots.py` parses `slotdefs[]` in `Objects/typeobject.c`: 88 entries that have a wrapper, with the macro doc expansions reproduced.
   - Why parse it instead of keeping a copy: it is the table the interpreter itself uses, so there is no second copy to drift. test_clinic checks the parse against every wrapper descriptor of the builtin types (the text signature and doc must match).
   - A spec dunder found in slotdefs is a slot. `__new__` and `__init__` are the exception: they stay clinic functions.
2. **Slot stubs.**
   - Written like `def __len__(self, /): ...`: parameters unannotated, because the C signature is the slot typedef and the compiler checks it.
   - Clinic checks the parameters against the wrapper's text signature from slotdefs, for example `__contains__($self, key, /)`.
   - A slot must not have a docstring: the wrapper's doc comes from slotdefs.
   - The C name defaults to `<class>_<slot minus prefix>`: `bytes_repr`, `bytes_length`, `bytes_richcompare`, `bytes_iter`.
   - If one dunder of a slot group is declared, all must be: the six comparisons for `tp_richcompare`, `__mod__`/`__rmod__`, `__mul__`/`__rmul__` for `sq_repeat`. A partial set is an error.
   - A return annotation, if present, uses the existing facts vocabulary. `bytes_iterator.__next__ -> New[int]` means an exact int and no Python code runs.
3. **`@c_name` is the one decorator for C names.**
   - `@c_name("x")` is clinic's `as x`. It also works for clinic methods, and replaces `B.center as stringlib_center`.
   - `@c_name(mp_subscript="bytes_subscript", sq_item="bytes_item")` picks the slots of a dunder that several slots can implement. It is required only in that case, and a group partner inherits the choice (`__rmul__` from `__mul__`).
   - `@c_name(METH_NOARGS="f")` or `@c_name(METH_O="f")` declares a hand-written PyCFunction entry. The flag is checked against `(self, /)` or `(self, arg, /)`. The docstring is used as is, with no signature added, and NULL if there is none.
   - Why keyword forms: one concept covers "which C function, with which C interface" for clinic functions, slots and hand-written PyCFunctions alike.
4. **Shared methods via plain Python import.**
   - `from stringlib.pyspec import ctype, transmogrify`, then `center = transmogrify.B.center`. The path is relative to the C file's directory.
   - `Objects/stringlib/pyspec/transmogrify.py` is the spec of `transmogrify.h`; the existing spec-path rule already covers `.h` files, which answers WS9's open question. Its generated `clinic/transmogrify.h.h` is byte-identical to before.
   - `Objects/stringlib/pyspec/ctype.py` declares the 13 `stringlib_is*`/`lower`/… PyCFunctions for bytes and, later, bytearray.
5. **`@static_type(member="C expression", ...)`.**
   - The keywords are PyTypeObject member names; unknown members are rejected, and so are members the spec derives. `@final` (typing.final) means no Py_TPFLAGS_BASETYPE.
   - Derived:
     - `tp_name` from the class name
     - `tp_basicsize = sizeof(<class-directive C type>)`
     - `tp_doc` from the class docstring
     - `tp_flags`: DEFAULT, plus BASETYPE unless `@final`, plus HAVE_GC when tp_traverse is given, plus any extra flags given
     - `tp_methods`, all slots, `tp_base` (from class bases)
     - `tp_new`/`tp_init`/`tp_vectorcall` from clinic
   - Output goes to `Objects/clinic/<stem>_types.c.h`, included at the end of the .c. It is a static, immortal type with designated initializers, not PyType_FromSpec. The type object and C type come from the `class` directive; `class bytes_iterator "striterobject *" "&PyBytesIter_Type"` was added.
   - Why a decorator: sizes, alloc/free/dealloc/traverse, the version tag and `_tp_iteritem` have no Python meaning and cannot be derived.
   - Why BYTES_SUBCLASS and MATCH_SELF stay explicit: deriving them would only move a hard-coded name list into clinic.
6. **Clones with no block are generated after their target**, so spec order can equal method-table order.

### The iterator and FOR_ITER
The iterator is spec class `bytes_iterator` (`@final`). The struct, dealloc, traverse and next stay C. `__length_hint__`, `__reduce__` and `__setstate__` are hand-written PyCFunctions whose docs are unchanged; converting them to clinic would add a text signature. I did not write spec bodies for them: they need struct-field access, which the emitter doesn't lower.

For FOR_ITER over bytes, the facts give: the loop variable is an exact int (a small immortal one in 0–255), and the iterator's next never runs Python code. So the optimizer could drop int type guards on the value and avoid escape/deopt handling around the call. I did not build a tier-2 consumer.

### Scaling to other types
- **What fits:**
  - PyLong_Type: nb_* groups, `tp_base` derived for bool via `class bool(int)`.
  - PyList_Type and PyUnicode_Type: sq/mp slots, iterator types, clinic `__init__`, `tp_new=PyType_GenericNew` via `@static_type`.
- **Where it breaks:**
  - METH_COEXIST dunders, e.g. `list.__getitem__`. A natural spelling would be `@c_name(mp_subscript=..., METH_O=...)`.
  - `__hash__ = None` (PyObject_HashNotImplemented).
  - `tp_getset`/`tp_members`: long has getsets. Clinic `@getter` exists but is not wired to the table; PyMemberDef has no spelling.
  - `__class_getitem__` needs METH_CLASS on a hand-written entry.
  - Unicode's two iterator types share one method table.
  - Module types need `tp_name` with the module prefix (possible via `@static_type`).
  - Heap types (PyType_FromSpec) are out of scope.
