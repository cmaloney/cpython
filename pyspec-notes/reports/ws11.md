## How the list/tuple path is derived

Your equivalence claim holds in the GIL build:
- The old fast path runs no Python, so restarting from item 0 via the iterator can't be observed.
- `PyNumber_AsSsize_t(item, NULL)` returns int and int-subclass items as they are, without calling `__index__`, and clamps overflow to the same `ValueError` message.
- The first failing item decides the outcome in the same order on both paths.
- Beyond the unit tests, all 94 difftest cases give identical results on the old and new interpreters, both through `bytes()` and through the C API `PyBytes_FromObject`.

The derived code:
- **Index loop.** For an exact list or tuple, the partial evaluator folds `iter(x)` away, iterates by index without creating an iterator, and deletes the now-dead `it = iter(x)`. For a list it re-reads the size on every item, as the list iterator does.
- **Per-item fast path.** The conversion statement is split into `if type(item) is int` / `elif type(item) is bool` / generic. The first two use an inline compact-int read; the range check and append are shared. I added `bool` because the old fast path also took bools (int subclasses) directly; without it, `bytes([True, False]*8)` was 18% slower.
- **Unknown argument type.** The iteration is versioned: exact list, exact tuple, then the generic call.

**Free-threaded build:** the derived version holds no critical section, because every loop body may call `__index__`. Wrapping each item in a lock would be pointless; lists use `_PyList_GetItemRef`. So all-int lists lose the atomic whole-list snapshot. That is a valid behaviour: it is what lists containing a non-int already got. The FT debug build (`build-ws11-ft`) passes test_bytes, test_capi.test_bytes and test_clinic, and a stress script (four threads calling `bytes(lst)` while two mutate the list) ran cleanly three times.

## Corrections to your assessment
- **`for item in it:` isn't exactly `PyIter_Next`:** a Python `for` first calls `it.__iter__()`, which C does not. I made the spec's `iter()` (runtime.py) return a wrapper so the spec, run as Python, only calls `__next__`. The difftest case `IterReturnsOdd` covers this.
- **Iteration facts are not stubs:** the stub rule "an exact static type never runs Python" is wrong for iteration, since generators are static types whose `__next__` runs Python. So `partial_eval.ITERATION` is an explicit table (list, tuple, dict, set, frozenset, range, bytes, bytearray, str, with item types where known). It isn't in the facts vocabulary; it belongs in those types' own specs later.

## Emitter and partial-evaluator changes
- **emit.py**
  - `for` loops lowered three ways: `PyIter_Next`, a list index loop (`#ifdef Py_GIL_DISABLED` → `_PyList_GetItemRef`), and a tuple loop with borrowed items. The loop variable is released right after its last use, as the hand-written code did.
  - Escapes can now be called as statements (int status), or initialize a C local in place, with a release statement and "steals" handling.
  - A cheaper lowering is used where the evaluator proved an argument's exact type.
  - A local may be assigned in exclusive branches (checked against holding a reference). Generic bodies now pass through the evaluator without inlining.
- **partial_eval.py:** refines types on `type(x) is K`, folds `iter()` for types in the table, specializes loops, versions unknown iterables, splits on item type, and removes dead `iter()` calls.
- **call_table.py:** facts for loops and escape statements; a dedup key that includes the evaluator's marks (otherwise the list and tuple variants would have merged).
- **runtime.py:** new escapes for the length hint, the appender and the exact-int/bool lowering, plus the `iter()` wrapper.
- **capi.py:** loops count as possibly running Python; the separate "sequence" behaviour category is gone, since lists and tuples now behave as ordinary iterables.

The emitted `bytes_from_iterator` has the same shape as the hand-written loop. Without the always-inline appender, clang left the appender's cursor in memory in the large generic function, costing about 24 instructions per item; `0c6e6820a13` fixes that.

`bytes(range)` gains most because the JIT now uses the no-Python call uop for it; test_opt was updated to expect that. Cycle counts were too noisy to report: identical code measured 1627 and 2210 cycles for the 256-item list.

**Open item: the list regression.** Lists cost about +4 instructions per item and about +100 per call:
- Each item is increfed and decrefed, because it must stay alive across a call that may run `__index__`.
- The size is re-read on every item.
- `PyObject_LengthHint` replaces the old direct size read.

Borrowing the item in the exact-int branch would need an "borrowed until Python may run" ownership rule in the emitter. I haven't done that.

## Other escapes (assessment only, nothing implemented)
- **`PyNumber_AsSsize_t`: high value.** A body would make every int subclass and bool Python-free and would derive the inline lowering I wrote by hand in runtime.py. It would also make `bytes(16)` run no Python: that entry still says "may run Python" only because its `except TypeError` fallback is assumed reachable, and an exact int can never raise it.
- **`PyUnicode_AsEncodedString`: medium, blocked.** With a constant `utf-8`/`ascii`/`latin-1` encoding and no custom error handler it runs no Python and returns exact bytes. But the call table skips calls with C-string arguments and has no per-constant entries, so the JIT couldn't use it yet.
- **`lookup_special`: low.** The evaluator already resolves it from the real type at clinic time; a body would only replace that hard-coded logic.
