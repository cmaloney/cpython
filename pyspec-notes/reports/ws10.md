## WS10 report: facts for refcount elimination, derived from spec bodies and used by the tier-2 optimizer

**Result:** the facts are now derived from the spec, conditioned on the exact argument type, and the tier-2 optimizer uses them. `bytes(b)` and `b.__bytes__()` on an exact bytes `b` no longer make a call. On a like-for-like PGO build, `bytes(b)` drops from 924 to 219 instructions per iteration. A bytes-subclass argument still gets the full call, and a test covers that.

All tests pass, with one exception: `-R 3:3` with the JIT on, which is broken on base. There is one design shortfall: the new `bytes.fromhex` facts are derived, but the optimizer never reaches that call.

### 1. Spec bodies (`Objects/pyspec/bytesobject.py`)
```python
    def __bytes__(self):
        if type(self) is bytes:
            return self
        return C.bytes_copy(self)

    @classmethod
    def fromhex(cls, string: object, /):
        result = C.bytes_from_hex(string)
        if cls is not bytes:
            return cls(result)
        return result
```
- The hand-written impls in `Objects/bytesobject.c` are gone. Clinic generates `bytes___bytes___impl` and `bytes_fromhex_impl` into `Objects/clinic/bytesobject_pyspec.c.h`, with the same C as before.
- **How clinic supports this:**
  - `dsl_parser.check_pyspec_method()` handles spec methods and class methods other than `__new__`. The self C type comes from the clinic class (`PyBytesObject *`) and is passed to emit through the new `app.pyspec_self_ctypes`.
  - `emit.describe_method()` does the method description. It belongs in `frontend.Spec.describe()`; I kept it in `emit.py` to stay out of `frontend.py`.
  - The emitter now lowers `f(x)` for an object or type variable (`cls(result)`) to `PyObject_CallOneArg`.
- **New escapes** in `runtime.py`: `bytes_copy` and `bytes_from_hex`.
- **Tests** in `test_clinic`:
  - `BytesSpecTest.test_dunder_bytes` / `test_fromhex` compare the spec with the interpreter, including subclasses.
  - `PyspecTest.test_method_and_class_method` covers the clinic side.

**Escape facts now live in the spec.** Each escape `C.<name>` gets its facts from a top-level stub of the same name, written in the catalog vocabulary. I added three things to that vocabulary:
- `New[bytes]`: the result has exactly that type.
- `RunsPython[T, 'p']`: Python code runs only through the slots of parameter p's type, so never for a static type.
- `@helper`: marks a C function that is not part of `bytesobject.c`'s C API (static, or defined elsewhere). The catalog skips it.

`runtime.stub_facts()` reads the stubs from the AST (clinic never executes the spec). With that, both separate tables are retired: `call_table.ESCAPE_FACTS` and `capi.ESCAPES_WITHOUT_PYTHON`. Two gaps remain:
- The error convention is still written twice: `Escape(error=)` in `runtime.py` and the stub's `OnError`. A test checks that they agree.
- "NULL without an exception means absent" (used by `lookup_special`) has no word in the vocabulary.

### 2. Derived facts
- **`partial_eval.py`:** folds `(func := C.lookup_special(x, "__bytes__")) is not NULL` when three things hold:
  - the exact type of x is a static type;
  - the attribute found is a spec method;
  - that method, evaluated for x, is only `return self` or a constant.

  The later `result = func()` is replaced by that value. A heap type, such as a subclass, is never folded, because its `__bytes__` can be overridden, even later. So `bytes(x)` with x exactly bytes evaluates to `return source` (`bytes_new_nargs1_bytes` is now just `Py_NewRef`).
- **`call_table.py`:** each entry now also carries `result_alias`. The table also has entries for the spec'd methods, keyed by `ml_meth` and found with `_PySpec_FindMethod()`.
- **`pycore_pyspec.h`:** gains `int8_t result_alias`, a `PyCFunction meth` union member, and `nmethods`/`methods` in the table.

| Entry | alias | constant | runs Python | exact type |
|---|---|---|---|---|
| `bytes()` | – | `Py_CONSTANT_EMPTY_BYTES` | no | bytes |
| `bytes(bytes)` | arg 0 | – | no (was: may) | bytes (was: unknown) |
| `bytes(bytearray/memoryview)` | – | – | no | bytes |
| `bytes(list/tuple/int/range/dict/float)` | – | – | may | bytes |
| `bytes(str)` | – | – | no, always raises | – |
| `bytes(x)`, generic (also used for subclasses) | – | – | may | – |

The conditioning self-test is `test_clinic.BytesSpecFactsTest`. It checks that for a plain subclass, a subclass overriding `__bytes__`, and an unknown argument type, `bytes(x)` gets neither the alias nor the exact type. That is the `_CALL_STR_1` failure mode. It also checks the `__bytes__` and `fromhex` facts, and that every escape has a stub whose error convention agrees.

### 3. Optimizer (`Python/optimizer_bytecodes.c`)
- **Alias, `_CALL_BUILTIN_CLASS`** (line 1773). When `result_alias == 0`, the argument type is guarded and the class is immortal, the call is removed and replaced by:
  1. `_MAKE_HEAP_SAFE`, only if the argument is borrowed;
  2. `_SWAP 3`.

  The argument's reference moves to the result slot and the class takes the argument slot, so both following pops become `_POP_TOP_NOP`. The existing speculation `_GUARD_TYPE` now triggers for bytes, because the result type is known.
- **Alias, `_CALL_METHOD_DESCRIPTOR_NOARGS`** (line 1950). The call is replaced by:
  1. `_COPY 1`;
  2. `_MAKE_HEAP_SAFE`, if borrowed;
  3. `_SWAP 3`.

  Otherwise the result gets the derived exact type or constant.
- **No Python code:** new `_CALL_BUILTIN_CLASS_1_INLINE_NO_PYTHON` (`Python/bytecodes.c:4897`), which does not escape.
  - It calls through `_PySpec_CallNoPython1()`, which I added to `NON_ESCAPING_FUNCTIONS` in `Tools/cases_generator/analyzer.py`.
  - It does not release the class, which is immortal.
  - The arguments already stay on the stack (gh-148171 was already applied to `CALL_BUILTIN_CLASS`).
- **Constants:** the existing `bytes()` folding is kept.
- **Tests in `test_capi/test_opt.py`:**
  - `pyspec_alias` and `pyspec_alias_owned_arg`;
  - `pyspec_alias_subclass`: the negative test, including a trace built for exact bytes and then fed a subclass;
  - `method_descriptor_noargs_pyspec_alias` and `pyspec_subclass`;
  - the updated `typed_variant` checks that the no-Python variant is used for bytearray and memoryview.

### Trace before → after (debug JIT build, loop body only)
- **`bytes(b)`:** `… _LOAD_FAST_BORROW _CALL_BUILTIN_CLASS_1_INLINE _POP_TOP_NOP _POP_TOP_NOP` → `… _LOAD_FAST_BORROW _GUARD_TYPE _MAKE_HEAP_SAFE _SWAP_3 _POP_TOP_NOP _POP_TOP_NOP`. No call.
- **`b.__bytes__()`:** `_CALL_METHOD_DESCRIPTOR_NOARGS_INLINE _POP_TOP_NOP _POP_TOP` → `_COPY_1 _MAKE_HEAP_SAFE _SWAP_3 _POP_TOP _POP_TOP_NOP`. No call. The remaining `_POP_TOP` is for the method descriptor: the optimizer loses its borrowed status earlier in the trace; this change doesn't cause it.
- **`len(bytes(b))`:** same as `bytes(b)`, followed by `_CALL_LEN` (unchanged).
- **`bytes(ba)`:** `_GUARD_TYPE _CALL_BUILTIN_CLASS_1_INLINE` → `_GUARD_TYPE _CALL_BUILTIN_CLASS_1_INLINE_NO_PYTHON`.
- **`bytes()`:** unchanged (already folded to `_LOAD_CONST_INLINE_BORROW`).
- **`bytes(sub)`:** unchanged; still calls `_CALL_BUILTIN_CLASS_1_INLINE` (the generic entry). This is the correct negative case.
- **`bytes.fromhex(s)`:** unchanged. The trace stops at a generic `_LOAD_ATTR` (class-method lookup isn't specialized), so the fromhex facts are never reached.
- **`sub.__bytes__()`:** unchanged; `CALL_METHOD_DESCRIPTOR_NOARGS` requires the exact type, so a subclass isn't specialized.

### Open problems
- **`fromhex` facts are unused:** the trace ends at `_LOAD_ATTR` for `bytes.fromhex`. Using them needs class-method `LOAD_ATTR` specialization plus a rule in `_CALL_BUILTIN_O`.
- **Facts that depend on a constant argument:** `_PyBytes_FromHex`'s result type depends on `use_bytearray`, so I added a second stub, `bytes_from_hex`, for the `use_bytearray=0` entry point.
- **Mixed commit:** `pycore_pyspec.h` in commit 2 already contains `_PySpec_CallNoPython1`, which is only used in commit 3.
- **Folding scope:** the partial evaluator only folds a lookup_special'd method whose body reduces to returning self or a constant. General inlining of non-tail spec calls isn't done.
- **Borrowed method descriptor:** `b.__bytes__()` still pops the method descriptor with `_POP_TOP`; the optimizer loses its borrowed status before this call.
- **No-Python escapes:** the facts are only as good as the stubs, and `_CALL_BUILTIN_CLASS_1_INLINE_NO_PYTHON` relies on them to skip `_SET_IP`/`_CHECK_VALIDITY` and the stack spill. `_PySpec_CallNoPython1` in the non-escaping list is an explicit trust boundary.
- **Class-method table entries:** they aren't pruned; `fromhex` has 11 entries whose facts only differ in the no-Python flag.
- **Worth reporting upstream (not fixed):** `_IS_OP` doesn't fold `r is b` when both sides are the same symbol. After the alias, `bytes(b) is b` could fold to True.

### How this generalizes
These are hand-written facts in `Python/optimizer_bytecodes.c` that per-argument-type partial evaluation of specs could derive instead:
- **`_CALL_STR_1`** (:1652), same shape as `bytes(x)`:
  - exact str argument → alias of the argument;
  - otherwise the result is a str of unknown exact type. Today it claims an exact str, which is the known use-after-free.
- **`_CALL_TUPLE_1`** (:2283): alias for an exact tuple argument; the fallback `sym_new_type(&PyTuple_Type)` is right, but only because tuple has no `__tuple__` hook.
- **`_CALL_TYPE_1`** (:1636): `type(x)` gives a constant result when x's type is known.
- **`_CALL_LEN`** (:2507): a constant length for known types and constants. A spec for `len` plus `sq_length` would derive it, including which arguments run no Python code.
- **Result types of binary/subscript/string-building ops:** `_BINARY_OP_ADD_UNICODE` (:488), `_BINARY_OP_SUBSCR_STR_INT` (:591), `_BUILD_STRING` (:2239). These are "exactly str" results a spec of the slot functions would give directly.
- **`_CALL_METHOD_DESCRIPTOR_O`** (:2059) and **`_CALL_BUILTIN_O`** (:1754) have no result facts today. The method table keyed by `ml_meth` added here is the mechanism. For example, `bytes.decode` → exact str, `str.encode` → exact bytes, and `__index__`/`__buffer__` would decide whether Python code runs.

Across all of these, the derived facts carry their condition (the exact argument type, and a static type for any special-method lookup). That is exactly what the hand-written `_CALL_STR_1` rule drops.
